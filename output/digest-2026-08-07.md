### Added
- [`df5b186`](https://github.com/valeriogalano/dispatch/commit/df5b1863355273c77df53d8582bed1f992814c11) feat: follow agent-skills main instead of a pinned commit
  A submodule always records a commit, but nothing forces the build to use it.
  Both workflows now fetch with --remote, so editing Engram changes how Engram
  writes without a bump commit here — which is the point of having one source
  rather than a copy.
  
  What this gives up is reproducibility of a past build, and here that costs
  nothing: the recaps are committed as files, so there is no artifact to
  rebuild, and a broken skill fails loudly at import instead of quietly
  producing a worse text.
  
  The prompt-composition test now asserts against the skill files rather than
  their wording, which is free to change upstream. The check on the absolute
  constraint stays coupled on purpose: dropping it should turn CI red.
- [`78bc2d1`](https://github.com/valeriogalano/dispatch/commit/78bc2d1fa65b748b9bd968f4418bb5dd178b2a9f) feat: compose Engram's prompt from the skill instead of a local copy
  The ENGRAM block and the two style prompts were a copy of the vault note kept
  by hand, so keeping them in sync was a discipline nobody could enforce. The
  agent-skills repo now carries Engram as a proper skill, split into identity,
  prose standards and per-role rules; this wires recap.py to it through a
  submodule and composes the system prompt from those files at import.
  
  The two user prompts shrink to naming the channel and handing over the digest:
  the link rules, the episode exclusion and the manual-updates rule now live in
  the role file, in one place instead of two.
  
  Both workflows that touch recap.py need the submodule checked out — the recap
  job to run it, the test job because importing the module reads the files.

- [`fa978a8`](https://github.com/valeriogalano/dispatch/commit/fa978a8607c18e069a2cff310f4d1211397d6886) fix: authenticate the skills submodule checkout with the PAT

  authenticated with the PAT would retrigger workflows that the default token
  deliberately does not.

- [`c9ce9f5`](https://github.com/valeriogalano/Timebox/commit/c9ce9f50ebeafd9ec22f5e439e082a5c51721459) feat(settings): make the hours/minutes input threshold configurable
  A bare number typed into an hours field is read as minutes once it exceeds a
  threshold, so "90" means 1h30 while "8" means eight hours. The threshold was
  hard-coded at 12; it is now a setting between 1 and 24, defaulting to 9. Values
  containing ":" stay explicit and never go through the threshold at all.
  
  Lowering the default from 12 to 9 changes what "10", "11" and "12" mean for
  anyone who has not set the value: they now read as minutes. That is the intended
  reading - ten-hour single entries are rarer than ten-minute ones - and the
  setting is there for whoever disagrees.
  
  The value lives in src/hours-threshold.js, mirroring src/slot-capacity.js: a
  default, a setting key, a normalizer, loaded once by App from the settings table
  and edited in Settings under Pianificazione. parseHHMM takes the threshold as an
  optional second argument and otherwise reads the module's current value, because
  it is called from eight places across six files and threading a prop through half
  the interface would cost more than the problem - the tests pass it explicitly so
  they do not depend on module state.
  
  Normalizing had to separate "absent" from "zero": getSetting returns null for a
  key that was never written, and Number(null) is 0, which is finite and would have
  been clamped up to 1 - making every typed number minutes on a first launch.
  
  Also removes parseHHMM from lib/domain.js. Nothing imported it and no test
  covered it, so it was dead code sitting one edit away from silently disagreeing
  with the renderer's now-configurable version.
- [`182d686`](https://github.com/valeriogalano/Timebox/commit/182d6867bbd8a78cee2c7caf8ebb497bedf1351b) feat(db): default the database to Documents/Timebox instead of userData
  The database is the user's own data and belongs where their backups already
  reach. userData is not backed up either, so keeping it there does not make the
  data any safer, and it is removed on uninstall or app reset - which would take
  the only copy of the tracking history with it. Documents survives both.
  
  On macOS this means the first launch triggers the TCC prompt for Documents. A
  denial surfaces through the existing "Impossibile aprire il database" dialog,
  from which another location can be picked, so the failure mode is already
  handled rather than silent.
  
  Existing installations do not move: openDatabase persists the resolved path to
  config.json on every non-dev launch, so from the second launch onwards
  config.dbPath wins over the default and this change is invisible to them.
  
  Development is unaffected - it keeps its own hard-coded timebox-dev.db in
  userData, because the unsigned node_modules Electron binary has no TCC grant for
  Documents and must never reach the real database.
  
  Documents the three paths in AGENTS.md as a table, including the warning that a
  timebox.db in the repository root is a gitignored leftover and not the app's
  database - a trap that already cost one round of wrong conclusions.
- [`326e27a`](https://github.com/valeriogalano/Timebox/commit/326e27a48328edc6e82425fb6967d67b5c057af7) feat(prospettiva): answer "when do I hit the caps" instead of projecting the template
  The lens now reads cumulative caps only - project total budgets and area global
  limits - showing consumed hours, remaining hours and an exhaustion band (within
  2, 4, 8 weeks, beyond) computed on the rhythm measured over the last 4 closed
  weeks.
  
  The previous projection carried no information. Against a weekly cap the
  projected/cap ratio is invariant in the horizon, because both sides scale by it:
  the 2/4 week selector could not change the verdict. The template rhythm also
  overstates the real one (INVALSI plans 14.25h/week against ~10.6h tracked) and
  does not exist at all for projects, since `recurring` maps areas only - which is
  why the project-level caps were absent from the lens and the monthly review had
  no screen answering "which projects are close to exhaustion".
  
  Weekly caps are deliberately out of scope here: they reset every week, so they
  are never reached cumulatively, and their useful number is the current week
  margin already visible in the Settimana lens.
  
  Bands rather than exact weeks: the measured rhythm carries an uncertainty wider
  than the distance between three and four weeks, so a precise figure would claim
  accuracy the data does not have. Two degenerate cases are named rather than
  computed - a cap already exceeded reads "esaurito" instead of a negative
  remainder, and a zero rhythm reads "fermo" instead of an Infinity printed as
  "beyond 8 weeks".
  
  Removes the horizon selector, the uncapped rows and areaProjection with its
  tests; replaces the two projected KPIs with remaining hours and remaining
  billable value.

- [`d76928d`](https://github.com/valeriogalano/Timebox/commit/d76928da4f63334acfadb1ebbe8507f19061f6b8) fix(prospettiva): stop double-counting nested caps in the totals, document the section

  from 404h30 to 568h and from EUR30,130 to EUR46,395.

  rows themselves still show every cap, since a nested budget is still a real
  budget to watch.

  renders one when a `help` prop is passed, and that section had none, so the one
  place explaining ordering, the measured rhythm, the partial-window note and the
  difference between "Fermo" and a distant exhaustion had no way in.
