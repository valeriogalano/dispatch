### Added
- [`b21c64e`](https://github.com/valeriogalano/Timebox/commit/b21c64edc15f8f6c20e4548458530be46bf90065) feat: warn about Timebox projects missing from Todoist on sync
  Every active Timebox project whose name is no longer among the current
  Todoist projects is surfaced as an alert after sync (archived, deleted,
  or renamed on the Todoist side are all indistinguishable, since the REST
  API only lists active projects). No automatic archiving; the maintainer
  decides.
  
  Also fixed fetchTodoistProjects to page through all Todoist projects
  instead of stopping at the first 200, which the new check depends on
  to be accurate.
- [`76253b7`](https://github.com/valeriogalano/Timebox/commit/76253b7aed2378c37d9d1c972a7a38d6dd5b6ad7) feat: auto-import Todoist projects and match new ones by area color
  getOrCreateTodoistClient always put a newly imported Todoist project in a
  generic "Todoist - <Color>" area, which has no hours in the recurring
  template, so its load stayed invisible. It now first looks for a single
  non-generic work area (excluding todoist-* ids) whose color equals the
  Todoist project's color, case-insensitive; with none or more than one
  match (several work areas can share a color, e.g. red), it falls back to
  the generic area as before. No new project is created for a Todoist
  project that already has a same-named Timebox project, archived included
  — unchanged.
  
  The todoist:sync IPC handler now calls q.importTodoistProjects(todoistProjects)
  before matching, so a Todoist project created since the last manual
  "Importa progetti" run is matched on this same sync. Matching reads the
  up-to-date project list from the DB instead of the renderer-passed one.
  When any project was added, every window gets a db:changed 'structure'
  notification so the renderer's project list refreshes without a restart.
  
  Completed-tasks time import (todoist:getCompletedTasks /
  importCompletedTodoistTasks) is untouched — it stays name-based on
  purpose, as documented.
- [`40f53e4`](https://github.com/valeriogalano/Timebox/commit/40f53e4d22f0295c8c659126a75f10fcc39e8f76) feat: surface Todoist tasks with no matching Timebox project
  The todoist:sync IPC handler (main.js) silently dropped every open task
  whose Todoist project had no Timebox project of the same name
  (`if (!proj) continue`), even though day_mismatches and the mismatches
  panel already know how to display an 'unmatched' matchStatus —
  getImportedTodoistTasks derives it whenever projectId is null, but the
  task never reached the cache to be derived.
  
  Such a task is now pushed into byDate with projectId: null,
  timeboxProjectName: null, todoistProjectName set, and matchStatus
  explicitly 'unmatched'. Tasks without a due time or without a duration
  are still skipped, unchanged.
  
  Traced every consumer of the cache: dayPlanning.js (used by TodayView,
  WeeklyView, PlanningCell) already drops a task whose projectId doesn't
  match any project before it can affect block capacity; day-free-capacity,
  day-ready-blocks and day-mismatches already gate on
  `matchStatus === 'matched'` for anything project-specific. No consumer
  needed a code change — they were already written to handle this shape,
  they just never received it.
- [`e4f5986`](https://github.com/valeriogalano/Timebox/commit/e4f59866fa1d3529f8a0f56f6e5d445674f4d750) feat: allow changing an area's color via MCP
  The MCP server could rename an area (rename_area -> PATCH /areas/:id) but
  not change its color, unlike the UI (Aree -> Aspetto).
  
  - PATCH /areas/:id (and the legacy /clients/:id alias) now accepts
    `color`, resolved server-side via a new resolveTodoistColor() in
    db/queries.js: a Todoist palette key (e.g. "lavender") or a hex from
    that palette, case-insensitive. Anything else is a 400. The validation
    stays server side because mcp-server.js is zero-dependency and must not
    load db/queries.js (better-sqlite3 ABI).
  - New MCP tool update_area (id + optional name/color, at least one
    required); rename_area is unchanged for compatibility. The tool
    description lists the valid color keys since mcp-server.js cannot
    import TODOIST_COLORS.
  - TODOIST_COLORS and resolveTodoistColor exported from db/queries.js.

- [`b3aadc9`](https://github.com/valeriogalano/Timebox/commit/b3aadc9012015b2ac5063d2eecb5ddbc354af32c) fix: make recurring block height proportional to hours
  PX_PER_H was 40 with a fixed 36px floor, which flattened every value
  below ~0.9h to nearly the same height — 0.5h and 1h were 36px and 40px,
  indistinguishable. Raised PX_PER_H to 64 and set the floor to
  0.5 * PX_PER_H, the exact height of the smallest hour value a block can
  have (blocks never go below 0.5h), so it never misrepresents a real
  value.
  
  Also fixed the hour label contrast: it used a 53%-opacity mix of the
  area color at font-size 9, barely readable on some areas. Aligned it
  to the same full client.color already used for the area name.
- [`e067bf2`](https://github.com/valeriogalano/Timebox/commit/e067bf225a430a02b5d05be7077e61e831995ef1) fix: collapse recurring overrides list by default
  The overrides list opened expanded and pushed the template grid down,
  even though the count is already visible in the summary and reviewing
  it is a weekly-routine step, not something to act on every time the
  screen opens.
- [`cc30e84`](https://github.com/valeriogalano/Timebox/commit/cc30e84dca8d1acd7456480f5136f741aa4829d9) fix: average divergence over the full history window, not just diverging weeks
  RecurringScreen computed avgDelta by dividing the sum of deltas by the
  number of diverging weeks only, inflating the shown deviation — with 3
  diverging weeks out of 8, the average was 3/3 instead of 3/8. A week
  with no override row used the template (delta zero) and must count in
  the denominator.
  
  This also changes what the Applica button writes into the recurring
  template, since it builds the new template from templateHours + avgDelta.
  
  Extracted the computation into src/divergences.js as a pure function,
  following the dayPlanning.js / panoramica-insights.js / slot-capacity.js
  pattern, with node:test coverage.
- [`d79f22c`](https://github.com/valeriogalano/Timebox/commit/d79f22ca9324ad5dde47e34271fc426f2b542236) fix: handle Todoist sync errors and drag-end cleanup, align budget meter thresholds
  - todoist:sync now propagates errors from the projects/tasks REST calls
    instead of silently matching against an empty/partial list, which was
    filling the day with false "unmapped" tasks.
  - importTodoistProjects skips Inbox and any project with children: they
    are organizational containers, never real work.
  - PlanningCell/TodayView/WeeklyView now clear drag state on dragend, not
    only on drop, so the dashed drop-target outline no longer sticks around
    after an internal reorder or a drop outside any slot.
  - Extracted a single budgetAlertLevel(50/80/100%) threshold in utils.js,
    replacing four inconsistent scales (one on a 0-100 base) across
    WeeklyView, PlanningCell and Dashboard. Dashboard now shows the meter
    from the first level and has a corrected tooltip.
  - avgDelta in RecurringScreen (dividing only by divergent weeks) is left
    as a decision for the maintainer, documented with real numbers in a
    Todoist comment rather than changed here.
  - AGENTS.md updated for both Todoist Integration behavior changes.
- [`918a26d`](https://github.com/valeriogalano/Timebox/commit/918a26d98f2ec5e23d0f8014465c13cc19d27332) fix: stop Sunday-keyed week_overrides from faking divergences
  week_overrides had rows keyed by Sunday (weekKey + 1 day off), likely from
  an old UTC-shifted write of a local Monday midnight. The recurring freeze
  walked past-week keys in 7-day steps from the earliest seen weekKey, so any
  Sunday key re-seeded a whole parallel Sunday series on every template
  change. Range readers (RecurringScreen "Override ripetuti",
  Panoramica "Da decidere") group by raw weekKey and counted these as extra
  weeks with stale, divergent data.
  
  - getUsedWeekKeys now only seeds from Monday-keyed week_overrides rows.
  - Migration re-keys orphan Sunday rows under their Monday twin
    (INSERT OR IGNORE, so an existing Monday row wins) and drops all
    Sunday-keyed rows afterwards.
  - POST /overrides (used by the MCP set_week_override tool) now rejects a
    non-Monday weekKey with 400 instead of accepting it silently.
  - cli/__tests__/recurring-freeze.test.js switched from toISOString() to
    local date formatting, which is what made the corruption reproducible
    under TZ=Europe/Rome in the first place.
- [`443f632`](https://github.com/valeriogalano/Timebox/commit/443f632c1a1c4f592bd038a45c73c4dc1dd98375) fix(planning): honor hours/minutes threshold in recurring block field
  The hours field of a recurring planning block parsed its draft with a
  hand-rolled parseFloat instead of parseHHMM, so it ignored the
  hoursMinutesThreshold setting and did not understand the colon form:
  with the threshold at 9, '90' created a 90-hour block instead of 1.5,
  and '1:30' parsed as NaN and was silently discarded.
  
  The NaN guard goes away with it: parseHHMM already falls back to 0, so
  the v > 0 check covers invalid input.

  regardless of what a command's `cd <dir> &&` or `git -C <dir>` actually

  repo whenever a commit ran against a different one, either wrongly

  substring before acting.
